# 📏 Project Rules & Contribution Guidelines
## Disaster Relief Resource Mapper

---

## 1. Git Rules

### Branch Strategy
```
main        ← production-ready only. Never push directly.
dev         ← active development. All PRs merge here first.
feat/xyz    ← feature branches off dev
fix/xyz     ← bug fix branches off dev
```

### Commit Message Format
```
type: short description

Types:
  feat     → new feature
  fix      → bug fix
  style    → UI/CSS changes only
  data     → data files / schema changes
  docs     → documentation only
  refactor → code restructure, no behavior change
  test     → testing

Examples:
  feat: add flood simulation water level slider
  fix: resource markers not rendering on zoom
  data: add Mumbai elevation CSV
  docs: update API schema for /reroute endpoint
```

### PR Rules
- Every feature = one branch = one PR
- PR must be reviewed by the other member before merge to dev
- No force pushes on main or dev
- Delete branch after merge

---

## 2. Code Standards

### Frontend (Swapnil)
- One component per file
- Components in `PascalCase.jsx`
- Hooks in `camelCase.js` with `use` prefix
- No inline styles — use CSS modules or CSS variables
- Every API call goes through `services/api.js` — no direct axios calls in components
- Console.log is fine during dev, must be removed before final submit
- If a component exceeds 150 lines, split it

### Backend (Zahid)
- One engine per concern (flood / cyclone / router — separate files)
- All route handlers in `main.py`
- All business logic in `engines/`
- All Pydantic models in `models/schemas.py`
- Every function must have a docstring (academic requirement)
- Return proper HTTP status codes (200, 400, 404, 500)
- Never hardcode region-specific logic — use the region parameter

---

## 3. API Contract Rules

- Any API change must be communicated to Swapnil **before** pushing
- Response shape must match SCHEMA.md exactly
- No breaking changes to existing endpoints without discussion
- New endpoints: add to SCHEMA.md first, implement second

---

## 4. Data Rules

- `resources.json` is always generated by `generate_data.py` — never edit manually
- Elevation CSVs are pre-fetched and committed — do not regenerate during runtime
- All synthetic coordinates must be realistic (within actual city bounding boxes)
- Status field is always one of: `"online"`, `"offline"`, `"damaged"`

---

## 5. Daily Workflow

```
Every day:
1. git pull origin dev
2. Create feature branch: git checkout -b feat/your-feature
3. Build your thing
4. Test it
5. git push origin feat/your-feature
6. Open PR to dev
7. Notify other member
```

---

## 6. Communication Rules

- Daily check-in (WhatsApp/Discord) — even just "still on track" or "blocked on X"
- If blocked for more than 2 hours — message immediately, don't waste time
- Any scope change must be agreed by both before implementing
- Zahid's API must be running before Swapnil needs it — coordinate timing

---

## 7. Academic Compliance

- Python must be the primary backend language (FastAPI = Python ✅)
- Core skills covered: File I/O ✅, CSV/JSON parsing ✅, basic mapping ✅
- README must clearly state: "Built with Python (FastAPI) + React"
- Both members must be able to explain any part of the code during evaluation
- No copy-pasting from online tutorials without understanding it
- GitHub commit history must show both members contributing
